# Share Text Agent Conventions

## Development Guide

Read this `AGENTS.md` and the applicable shared reference files under `$AI_CONFIG_DIR/references/*.md` before writing or reviewing code. When reviewing code, follow the `code-review` skill definition, reporting findings with severity, location, rule, and fix. When instructions are ambiguous about what to change or how to approach a task, ask the user to clarify or present up to three concrete options before making changes, to avoid unwanted edits. This includes how an element is displayed: if the rendering convention for a value is not established (e.g. the document type shown to visitors), ask before guessing a visual style.

## Project conventions

- Code changes are applied in a separate git branch and worktree under `.worktrees/` per the shared `references/git.md` worktree practice, unless the user opts to apply them on top of the current worktree. Create worktrees with `node scripts/create-worktree.mjs <branch>` from the default worktree; it copies the gitignored local dev files (`.env.dev`, `backend/.env.dev`, and all files under `.data/`) and sets `DEV_TAG=<branch>` in the new worktree's `.env.dev` so the bottom-left worktree-tag block identifies the branch.
- Server persistence goes through the `Db` interface (`src/lib/server/db-types.ts`), writing engine-agnostic SQL with `$n` placeholders and `current_timestamp` so DDL stays portable across adapters. Follow the SQL conventions in `references/sql.md` (including binding a placeholder once per occurrence). Multi-statement writes that must be atomic go through `db.transaction(fn)`, running every statement against the injected query (never `getDb().query`) so the sequence stays on one connection; the SQLite adapter serializes all statements so a transaction cannot be interleaved.
- Mutations are logged via `$lib/server/logging` with key identifying info (document id, name, size, IP, `elapsed_ms`).
- Document tags are stored as a JSON array of `{ name, color }` objects in the `documents.tags` column; `color` must be one of the hex `TAG_COLORS` in `src/lib/tag-colors.ts`, and chips/dropdowns render via the `tagChipStyle`/`tagDotStyle` inline-style helpers there (class helpers `tagChipClass`/`tagDotClass` carry the non-colour base styles). Tag badges render with the `Chip` component (`src/lib/components/Chip.svelte`).
- Document types follow the shared `type-registry` reference: the closed value set lives in `src/lib/document-type-values.ts`, the type definitions (language extensions, validators, formatters, converters, preview, toolbar actions) in `src/lib/document-types.ts`, and pure parse/format utilities in `src/lib/document-type-utils.ts`. Each type entry lazy-loads heavy dependencies (language modes, parsers) via dynamic `import()` inside the definition so they are not in the initial bundle. Consumers dispatch through `getDocumentType(value)` and never branch on specific type values.
- Editor preview modes are driven by the `preview`/`editor` URL query params via `usePreviewMode` (`src/lib/components/use-preview-mode.svelte.ts`). The toolbar always shows two toggle buttons (Editor view / Preview view), never a cycle button, each carrying `aria-pressed` and `disabled` when it is the sole active pane; the toggles/preview params are ignored for layout when the type has no preview. Split layout and `Splitter` orientation are documented in `docs/spec.md`.
- Editable form dialogs that persist data on Apply/OK (settings, tags, sharing, admin edit user/document) use the OK/Apply + Reset pattern and the discard-unsaved-changes confirm-on-dismiss behavior from the shared `ui-patterns` reference. Action dialogs that mutate data only on confirm (e.g. the document format dialog) skip both the discard confirm and the disabled-when-clean primary: dismissing loses only a parameter, and confirming the unchanged parameter is still the intended action.
- Form inputs place the caret at the end of the value when focused by keyboard (Tab/Shift+Tab) rather than letting the browser select the whole value: attach the shared `useCaretAtEndOnKeyboardFocus` action (`src/lib/components/use-caret-at-end-on-keyboard-focus.svelte.ts`) to the form's container, never per-input (mouse-initiated focus keeps its natural caret via the action's mousedown suppression).
- Dialogs built on `BaseDialog` are dismissed by its close affordances (top-right close icon, overlay click, Escape), all wired to the same `onCancel`; never add a footer Cancel/Close button that duplicates that `onCancel` — a footer action must do something distinct (persist via OK/Apply, reset, or confirm). `ConfirmDialog` therefore renders only its confirm action button.
- Content versions are keyed by the immutable numeric `documents.id` (never the app-facing key) so an admin key change never migrates version rows; only the newest `MAX_DOCUMENT_VERSIONS` (default 20) snapshots are kept per document. The version data model and `HistoryDialog` behavior are documented in `docs/spec.md`.
- Overlay option panels (dropdowns, tag suggestions) position via the shared `positionPanel` action (`src/lib/position-panel.svelte.ts`): attach it to the panel with `use:positionPanel={() => ({ getTrigger, getOpen, align?, autoPlace? })}` and keep the `fixed left-0 top-0 z-50 will-change-transform` classes on the panel. Trigger-and-item overlay menus (the three-dot `KebabMenu` and the globe `LanguageMenu`) share the `Menu` primitive (`src/lib/components/Menu.svelte`), which owns the trigger button, `positionPanel` panel, open/close/toggle, roving real-focus navigation (open on ArrowDown, ArrowUp/ArrowDown/Home/End with disabled-skip, hover syncing `activeIndex` and focus), and Escape/outside-pointer/scroll dismissal with focus returned to the trigger; new menus should be thin `Menu` instantiations, never a re-implementation. `SelectDropdown` is the combobox family (its own component, `aria-activedescendant` highlight, no roving focus) — do not fold it into `Menu`. The positioning/behavior mechanics are documented in `docs/spec.md`.
- Icons live as single-purpose components in `src/lib/icons/` (e.g. `PlusIcon.svelte`, `RefreshIcon.svelte`, `ChevronDownSmallIcon.svelte`), one component per glyph, each taking an optional `className` prop and rendering an `aria-hidden` SVG with `currentColor` fill/stroke. Every icon used in the project — including single-use ones — is a component in that directory. When a change involves an icon, reuse an existing component from `src/lib/icons/` if the glyph already exists, otherwise add a new component there; never inline an SVG in a component. `Button` renders icon snippets inside its `icon()` snippet and sizes them via `[&_svg]:h-full`, so icon components need no default size class; direct (non-Button) usage passes a sizing `className`. The `Spinner` component stays in `src/lib/components` (it is a loading indicator, not an icon glyph).
- Buttons that would move focus away from the editor (preview toggles, mobile drawer button, list-collapse button) pass the `Button` `preventFocusSteal` prop, which calls `preventDefault` on `pointerdown` so the button never takes focus while `click` still fires; raw non-`Button` controls that must not steal focus (e.g. listbox option buttons) use `onpointerdown={e => e.preventDefault()}` for the same effect.
- Every focusable element carries `outline-none` and a `focus:` state mirroring its `hover:` styles (e.g. `focus:border-cyan-500`, `focus:text-cyan-300`), so keyboard focus never shows the native outline and reuses the established hover indicator; elements with no hover style get an explicit cyan-ring or color-shift focus indicator instead (see the shared `accessibility` reference). Icon-only containers are sized by padding + glyph (`p-*`), never fixed `h-* w-*`; when a compact visual box is needed, extend the tap/keyboard hit area with `before:-inset-*` rather than enlarging the box (see the shared `responsive-design` reference).
- The CSV grid model (`src/lib/components/use-grid-model.svelte.ts`) tracks per-cell `committed` flags so pure navigation never serializes trailing empty cells into the CSV; preserve the self-echo reconciliation (an incoming `value` differing only by trailing all-empty rows is treated as a self-echo, not a rebuild). The full model mechanics are documented in `docs/spec.md`.
- The `DataGrid` component (`src/lib/components/DataGrid.svelte`) renders the CSV and Properties grids. Sorting uses the shared two-arrow header pattern via `model.sortRows(columnIndex, direction)` (explicit direction, no toggle); column-width math must subtract `TABLE_LEFT_BORDER` (1px) because the table's outer edges come only from `border-t`/`border-l`. Cell editors are `<textarea>`s (an `<input>` cannot hold `\n`): `Shift+Enter` inserts a newline, `Enter` commits and moves down. Resizable columns use the shared fixed-layout + `<colgroup>` model via `createColumnResize` (`src/lib/components/use-column-resize.svelte.ts`), with widths persisted via `$lib/column-width-storage.ts` when a `storageKey` is set, and the resize observer must watch the outer viewport, never the body wrapper. All mechanics are documented in `docs/spec.md`.
- Effects that reconcile an external input into editable `$state` (e.g. `CsvPreview` re-parsing `content` into grid rows) follow the `$effect` state-write guard from the shared `svelte` reference: track the last consumed input so each change is parsed at most once, since non-round-trippable text (like content shown after a type switch) would otherwise loop forever.
- The admin `DataTable` (`src/lib/components/DataTable.svelte`) sorts via the shared two-arrow header pattern, passing the explicit direction through `handleSortClick(column, direction)`. Derived column widths/min-widths are applied as inline `style` on cells, never runtime-built utility classes (see the shared `tailwind` reference). Resizable columns (opt-in via the `resizable` prop) reuse the shared `createColumnResize` composable, keeping the checkbox column fixed and honoring each column's numeric `minWidth`; a `storageKey` persists widths via `$lib/column-width-storage.ts`. Behavior is documented in `docs/spec.md`.
- The browser layout (`src/routes/(browser)/+layout.svelte`) is responsive: the first page of summaries is preloaded server-side and seeded into `useDocuments` (falling back to a client `refreshList()` when no seed was provided), and below the `md` breakpoint the panes collapse into full-screen pages, with the document list reachable via a `MobileDrawer` that reuses the shared `documentList` snippet. Pane visibility on mobile is expressed with literal CSS breakpoint classes (`hidden md:flex` on the editor pane and list wrapper, `md:w-[var(--aside-w,100%)]` on the list) so the SSR first paint is correct without JS; `isMobile` only drives the drawer, splitter, and editor toolbar layouts. Its Escape handling follows the shared dialog keydown protocol so it never double-fires with `BaseDialog`. Layout and responsive behavior are documented in `docs/spec.md` and `docs/design.md`.
- The admin console (`src/routes/admin/`) keeps its General/Properties/Documents/Users/Text To Speech tabs as real SvelteKit routes behind a `+layout.server.ts` guard, redirects unauthenticated sessions to the shared `/login` page, and holds `useAdminPreferences`/`useAdminSettings`/`useAdminDocuments`/`useAdminUsers`/`useAdminSegments` plus the `useAdminAuth` state machine in `+layout.svelte` so the general/settings drafts, documents/users data, and the Segments input survive tab switches. The shared `Tabs` component serves both route-driven console tabs (links keyed by `pathname`) and a state-driven mode (button tabs with `aria-pressed`; omit `pathname`). The General tab edits the admin account's preferred language through the server-persisted `GET`/`PUT /api/admin/preferences` API (`admin_preferences` table keyed by admin username) and uses the same Apply/Reload/Reset footer pattern as other editable settings screens. The admin edit-document dialog lays **Details** (header fields plus a document-type dropdown, an `isPublic` visibility checkbox, and an editable **Shared with** combobox) and **Content** (lazily loaded `CodeEditor`) out as two responsive panes — side by side, flowing Content below Details when the dialog is too narrow for both — and doubles as the add-document dialog (`mode` prop). The admin Properties tab uses the same state mode to split **Form** from **Properties** (a code editor) as two views of one shared draft: the `useAdminSettings` composable holds the editor text (`propertiesText`) and reconciles both directions with the self-echo guard — editor edits are parsed back into the draft (unknown settings are reported in a live banner and never pushed), while form edits/Apply/Reload/Reset resync the editor text — and the Apply/Reload/Reset footer is shared below the sub-tabs. The admin Documents and Users tables are deletion-toolbar-driven: no per-row delete buttons — a **Delete selected** toolbar button (enabled when `selectedCount > 0`) bulk-deletes via `confirmBulkDelete` — and neither tab has an action column, each toolbar **Edit** button resolving via `handleToolbarEdit` (Users: single selection opens that user's edit dialog, multiple opens the batch status dialog; Documents: enabled only with exactly one selection, opening that document's edit dialog). On touch-only devices (`useSupportsHover`, the `(hover: hover)` capability) copyable/editable admin cells render as plain values (`PlainCell`). The admin Text To Speech tab (`AdminTextToSpeechView` + `useAdminSegments`) is a client-side text→TTS-segment debug tool: it splits pasted text with `splitTtsSegments` using the runtime `tts_max_segment_length` resolved from `/api/tts/capabilities` and lists each segment's index, language, and inclusive `indexStart`–`indexEnd` range. The Segments view is a sub-tab within the Text To Speech tab (following the same `Tabs` state-driven pattern as the Properties Form/Properties sub-tabs). Numeric runtime settings accept thousand separators (`7,000`) in the Properties form, the Properties editor, the settings API, and the backend resolution — every number parser strips commas before `Number`/`int`.
- Document access control is enforced server-side through `resolveDocumentAccess` (`src/lib/server/documents.ts`), which returns `canView`/`canEdit`/`canDelete`/`canManageAccess` for a `Viewer` (`src/lib/server/viewer.ts`). Anonymous viewers own a document only when `owner_user_id is null` and `created_by` matches their IP but can never manage access (`canManageAccess` is always `false` for them), so the Share dialog/button and the access API are login-gated; registered users own via `owner_user_id`, can edit any public or shared document, and delete/manage only what they own; an admin viewer bypasses access entirely (no visibility filter). Documents default to `is_public = true`; only a logged-in owner (or admin) may change visibility or the share list. Route handlers resolve the viewer once and pass the resulting flags through — the client `owned`/`editable` flags come from the listing/load data, never a client-side guess. Sharing resolves sharees by username or email; an admin may share with any registered user including inactive (`setDocumentAccess`'s `includeInactive`), and the access `PUT` — as well as the `sharedWith` field of the admin edit-document `PUT` — is all-or-nothing: it rejects the whole update with 400 (listing the unresolvable sharees) rather than partially applying or silently dropping them. The user directory search (`/api/users/search`) is admin-only; the Share dialog seeds normal-user suggestions from previously-shared active users (`/api/users/recent-sharees`) and never enumerates the directory.
- Sharee inputs — the Share dialog and the admin edit-document dialog's **Shared with** field — use the shared `ShareeCombobox` component (`src/lib/components/ShareeCombobox.svelte`), which owns the debounced suggestion search, add/remove chip editing, and colored chip rendering; consumers pass a `search(query) => Promise<User[]>` provider (directory search for admin contexts, previously-shared users for the Share dialog) rather than re-implementing the combobox.
- User accounts live in the `users` table (unique lowercase `username` and `email`, `status` default `'active'`); sharing and per-user config use the `document_shares` and `user_config` tables. User auth (`src/lib/server/user-auth.ts`) uses a signed `sub`-carrying session token separate from the admin token; `src/lib/server/password.ts`/`rate-limit.ts` hold the shared password-hashing and login rate-limit primitives (re-exported by `admin-auth.ts`), with limits persisted in the `login_attempts` table. Inactive users are rejected at login and excluded from user search, share resolution, and viewer resolution. The admin Users tab manages users through `/api/admin/users` (create, update username/email/password/status, delete; deleting a user leaves documents ownerless and removes share rows via cascade).
- Per-account preferences (the UI preferred language in `user_preferences.preferred_language` and the Read aloud voice per language in `user_tts_voices`) persist through the login-gated `GET`/`PUT /api/user/preferences` API and the `$lib/server/user-config.ts` module: `normalizePreferencesInput` structurally validates the body (preferred language against the fixed `en`/`zh-CN`/`zh-TW` set, `ttsVoices` as a string-value object with empty strings dropped) and `saveUserPreferences` applies the whole preference set atomically via `db.transaction` (upsert the preference row, delete all voice rows, re-insert the posted ones). The PUT is logged as `user_preferences_save`. The user settings page (`/settings`, layout-server guarded like `/admin`, redirecting admins to `/admin` and anonymous to `/login`) reuses the shared `Tabs` for route-driven General/Read aloud/Documents tabs, keeps its preferences draft in `useUserSettings` (`src/lib/use-user-settings.svelte.ts`), keeps its owned-documents management state in `useOwnedDocuments` (`src/lib/use-owned-documents.svelte.ts`), shares the Apply/Reload/Reset footer across General/Read aloud, and uses a toolbar-driven Documents tab backed by `GET /api/user/documents` plus ownership-gated `PUT`/`DELETE /api/user/documents/[id]`. A 401 from the preferences or owned-documents APIs signs the session out. The preferred language is applied on sign-in (`useUserAuth` calls `setLocale`). The account button in the document list/collapsed rail is a single Settings gear (admin → `/admin`, user → `/settings`).
- Booleans are bound as parameters only through the `Db` interface; the SQLite adapter converts boolean params to `0`/`1` (`src/lib/server/db-sqlite.ts`) so `is_public = $1` stays portable, while literal `true` in SQL works on both backends. The admin documents table exposes an editable `is_public` column; admin routes bypass viewer access control.
- Admin document/user imports and exports use the same record shapes so an export round-trips through import: documents as `{ key, name, content, documentType, tags, isPublic }`, users as `{ username, email, status, passwordHash }` (the scrypt hash is exported so credentials survive a re-import; plaintext passwords never leave the server). The toolbar **Export** button passes the selected ids when any are chosen, otherwise exports all records. Document import accepts an optional `key` (validated for batch uniqueness, upserting into the existing document when it already exists); user import enforces batch uniqueness for `username` and `email` and accepts `password` or `passwordHash` (never both).
- `sql/schema.sql` is the source of truth for the dev schema. `createSqliteDb` in `src/lib/server/db-sqlite.ts` applies it idempotently (`create table if not exists`) on open, so the dev DB file persists across restarts and dev data survives. New tables appear automatically on the next open, but column changes to existing tables are not applied (SQLite lacks `add column if not exists`); apply those as incremental DDL from the temporary scratch script `.tmp/sqlite-dev.sql` before restarting the dev server. To fully reset the dev DB, delete `.data/share-text-dev.sqlite` and restart. Prod migrations live in `src/lib/server/db.ts` and are additive only (`create table if not exists` / `alter table ... add column if not exists`) so a running app never drops or rebuilds the database.
- The Read aloud feature proxies an external TTS service through the same-origin `/api/tts/*` endpoints; the service base URL is the `tts_service_url` runtime setting (DB override in `app_config`, else `TTS_SERVICE_URL` env, else empty) resolved by `getSettingStringValue` in `src/lib/server/settings.ts`, and every endpoint (and the client button) is gated on it being non-empty so the feature stays disabled until configured — admin can set/clear it in the Properties tab in real time.
- The Read aloud client groups the text into language segments (`splitTtsSegments` in `src/lib/tts-language.ts`): scan character by character into latin/CJK runs (a run touching kana is ja, pure Han is zh, else en) so unspaced text like `Hello你好世界` splits into en + zh while `こんにちは世界` stays one ja segment, merge adjacent same-language runs across single line breaks, fold short runs (English < 4 chars, CJK < 2) into the dominant surrounding language, split paragraphs into separate segments at blank lines, split any paragraph still over `MAX_SEGMENT_LENGTH` (500 chars) on sentence boundaries so no request is oversized, and strip newlines inside CJK segments so Chinese/Japanese read as one continuous sentence (English keeps its newlines); each segment's text is trimmed of leading/trailing whitespace and carries `indexStart`/`indexEnd` (inclusive, 0-based offsets into the original text, tracked through run merging/folding, paragraph splits, newline stripping, and sentence chunks) mapped to that trimmed span so text and range always agree and requests can log exactly which part of the document is spoken; keep segment generation pure and tested in `$lib` and never branch playback on hard-coded line counts. Human-readable TTS language labels (en, en_gb, zh, ja, yue) come from the shared `ttsLanguageLabel` helper in `src/lib/tts-language.ts`, reused by the admin Segments view and the user Read aloud settings.
- The Read aloud client synthesizes segments through a streaming async generator (`synthesizeTtsStreaming` in `src/lib/tts-client.ts`) that keeps a bounded pool of at most 4 in-flight requests (`SYNTHESIS_CONCURRENCY`) and yields each segment's blob as soon as it completes in input order, so the first segment plays before the rest of the document is synthesized; every request carries the segment's 0-based `segmentIndex` plus its `indexStart`/`indexEnd` (and the optional `voice`), which the proxy forwards snake_case (`segment_index`/`index_start`/`index_end`) for backend logging; `synthesizeTtsCached` collects the generator for callers that want all blobs at once. The per-segment audio cache stays bounded (LRU-style at 100 entries keyed by text + lang + voice storing the returned `Blob`); create object URLs from the blobs for playback and revoke them on stop/unmount.
- The Read aloud button has three phases: a Preparing spinner while synthesis runs before any audio, then a Stop toggle once the first segment plays; the Stop toggle (aria-pressed) is active during both phases and clicking it aborts in-flight synthesis and pauses playback.
- The TTS backend (`backend/`) keeps a process-level in-memory LRU cache (1000 entries, keyed by `sha256(lang + "\0" + text)`) of synthesized Piper audio bytes; cache hits skip `engine.speak` entirely and return the stored bytes. `POST /api/synthesize` returns audio in memory (writes to a `BytesIO`) and writes nothing to disk, so there is no output-path/`/api/audio` round trip; the cache makes the service effectively stateless across identical requests within a process lifetime (multi-instance/serverless-safe, cache warms per instance). It reads the `tts_max_segment_length` runtime prop from the `app_config` table read-only (`backend/app/db.py`, SQLite when no `DATABASE_URL` is set else Postgres, cached 5 s; `backend/app/settings.py` falls back to `TTS_MAX_SEGMENT_LENGTH` env then 500) and rejects over-limit requests with 422 — never write to the DB, a read failure resolves to the fallback so the backend never crashes. Piper is the only engine; it is cached at the process level (`get_engine` in `backend/app/engines.py`, keyed by model dir) so concurrent segment synthesis loads each voice once instead of per request; guard lazy voice loading with the engine's lock and never construct a fresh engine per request. `engine.speak` pre-sets the WAV header (16-bit mono at the model's sample rate) so a request that yields no audio chunks (e.g. punctuation-only text) returns a valid empty WAV instead of raising `wave.Error`. Voices are known upfront from `PIPER_VOICES` (`backend/app/engines.py`, one filename per language with per-language aliases like `en_gb`/`yue`): a language is synthesizable only when both its `.onnx` and `.onnx.json` exist in the model dir (`piper_lang_available`), and a request for a specific voice is rejected with 422 when that voice's files are absent (`piper_voice_available`) — a missing voice returns 503 rather than failing the request.
- The TTS backend logs synthesize events via `backend/app/logging.py` in the same line format as the front-end `logEvent` (`<timestamp> <level> ip=<ip> action=<action> key="value" ...`, default `INFO`, `ERROR` for `*_error` actions, client IP from `x-forwarded-for` then `request.client`): `tts_synthesize_start` fires on entry carrying `lang`, `text_size`, and `engine` (always `"piper"`); `tts_synthesize_end` carries `lang`, `engine`, `model` (the piper voice filename from `engine.model_name(lang)` on miss, or `"cache"` on hit), `text_size`, `elapsed_ms`, and `cache` (`"hit"` or `"miss"`); every failed request logs `tts_synthesize_error` with `error` and `elapsed_ms`. When the request carries the optional `segment_index` (0-based) and `index_start`/`index_end` (inclusive text ranges), log them in the start/end/error events so exactly the spoken span is identifiable. This is the async-op `_start`/`_end` pair convention from the shared `logging` reference — the start captures intent/identifiers, the end/error captures `elapsed_ms` and outcome. Keep both `log_event` and `get_request_ip` there and reuse them in `routes.py` rather than re-implementing the format.
- UI text in both the browser app and the admin console goes through `t()` from `$lib/i18n.svelte` (locales `en`, `zh-CN`, `zh-TW`, persisted in `localStorage` under `share-text:locale`). Follow the shared `svelte-i18n` reference: the source dictionary is `as const` and the other locales are typed `Record<MessageKey, string>` so a missing translation fails the build; `initLocale()` runs in the root layout's `$effect` (SSR always renders English to avoid hydration mismatch); and `t()` is called in templates/`$derived`, never in a `$props()` default — shared-component default labels resolve via `$derived(prop ?? t('key'))`. English-count pluralization (e.g. "{n} document(s)") is handled with singular/plural key pairs chosen by the caller; setting labels/descriptions are translated client-side via the `settingLabel`/`settingDescription` helpers (`setting.<key>` message pairs, `settingLabel(key) ?? setting.label` fallback in `AdminPropertiesView` and the `useAdminSettings` toasts/validation), while messages produced by the server (API `error` fields) stay English. The language selector is the `LanguageMenu` component (`src/lib/components/LanguageMenu.svelte`, globe icon, `positionPanel` menu) rendered in the document-list header, the collapsed rail, and the admin console header; document type labels and format titles stay untranslated.
- Temporary scratch files created during work (plans, proposals, scratch notes) go in the `.tmp/` folder, never in source directories.

## Keeping references in sync

- When a code change establishes or revises a project-specific convention, update this `AGENTS.md` in the same change.
- When a code change establishes or revises a generic reusable convention, update the appropriate file under `$AI_CONFIG_DIR/references/` in the same change rather than duplicating it here.
- Shared reference files under `$AI_CONFIG_DIR/references/` must remain generic and implementation-agnostic. Do not include project-specific file paths, component names, routes, or other internal identifiers in those references — put project-level details in this `AGENTS.md` instead. See `ai/references/README.md` for the brief style guide.
- This `AGENTS.md` holds project-specific *development conventions* — rules an agent must follow when writing code — not feature descriptions, implementation narratives, or user-facing behavior. Keep each bullet to the rule plus the briefest rationale. Implementation/architecture detail belongs in `docs/spec.md` and user-facing behavior in `docs/design.md`; generic reusable rules belong in `$AI_CONFIG_DIR/references/`.
