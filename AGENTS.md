# Share Text Agent Conventions

## Development Guide

Read this `AGENTS.md` and the applicable shared reference files under `$AI_CONFIG_DIR/references/*.md` before writing or reviewing code. When reviewing code, follow the `code-review` skill definition, reporting findings with severity, location, rule, and fix. When instructions are ambiguous about what to change or how to approach a task, ask the user to clarify or present up to three concrete options before making changes, to avoid unwanted edits.

## Project conventions

- Code changes are applied in a separate git branch and worktree under `.worktrees/` per the shared `references/git.md` worktree practice, unless the user opts to apply them on top of the current worktree. Create worktrees with `node scripts/create-worktree.mjs <branch>` from the default worktree; it copies the gitignored local dev files (`.env.dev` and all files under `.data/`) and sets `DEV_TAG=<branch>` in the new worktree's `.env.dev` so the bottom-left worktree-tag block identifies the branch.
- Server persistence goes through the `Db` interface (`src/lib/server/db-types.ts`), writing engine-agnostic SQL with `$n` placeholders and `current_timestamp` so DDL stays portable across adapters. Follow the SQL conventions in `references/sql.md` (including binding a placeholder once per occurrence). Multi-statement writes that must be atomic go through `db.transaction(fn)`, running every statement against the injected query (never `getDb().query`) so the sequence stays on one connection; the SQLite adapter serializes all statements so a transaction cannot be interleaved.
- Mutations are logged via `$lib/server/logging` with key identifying info (document id, name, size, IP, `elapsed_ms`).
- Document tags are stored as a JSON array of `{ name, color }` objects in the `documents.tags` column; `color` must be one of the hex `TAG_COLORS` in `src/lib/tag-colors.ts`, and chips/dropdowns render via the `tagChipStyle`/`tagDotStyle` inline-style helpers there (class helpers `tagChipClass`/`tagDotClass` carry the non-colour base styles). Tag badges render with the `Chip` component (`src/lib/components/Chip.svelte`).
- Document types follow the shared `type-registry` reference: the closed value set lives in `src/lib/document-type-values.ts`, the type definitions (language extensions, validators, formatters, converters, preview, toolbar actions) in `src/lib/document-types.ts`, and pure parse/format utilities in `src/lib/document-type-utils.ts`. Each type entry lazy-loads heavy dependencies (language modes, parsers) via dynamic `import()` inside the definition so they are not in the initial bundle. Consumers dispatch through `getDocumentType(value)` and never branch on specific type values.
- Editor preview modes are driven by the `preview`/`editor` URL query params via `usePreviewMode` (`src/lib/components/use-preview-mode.svelte.ts`). The toolbar shows two toggle buttons (Editor view with a pencil icon / Preview view with an eye icon), never a cycle button, on both desktop and mobile: each carries `aria-pressed` and switches its button variant to show on/off state, and is `disabled` when it is the sole active pane (so the panes can never be both off). Toggling a pane on always lands in split view. When the current document type has no preview support, the buttons and preview params are ignored for layout (the editor fills the full pane). The split layout and `Splitter` orientation are documented in `docs/spec.md`.
- Editable form dialogs (settings, tags, format, admin edit user/document) use the OK/Apply + Reset pattern and the discard-unsaved-changes confirm-on-dismiss behavior from the shared `ui-patterns` reference.
- Confirm dialogs (`ConfirmDialog`) render only the confirm action button; cancellation is served by the `BaseDialog` close affordances (top-right close icon, overlay click, Escape), all wired to the same `onCancel`. Do not add a footer Cancel button that duplicates that `onCancel`.
- Content versions are keyed by the immutable numeric `documents.id` (never the app-facing key) so an admin key change never migrates version rows; only the newest `MAX_DOCUMENT_VERSIONS` (default 20) snapshots are kept per document. The editor History button appears only when the document has 2+ versions (`versionCount`, refreshed after each save). The version data model and `HistoryDialog` behavior are documented in `docs/spec.md`.
- Overlay option panels (dropdowns, tag suggestions) position via the shared `positionPanel` action (`src/lib/position-panel.svelte.ts`): attach it to the panel with `use:positionPanel={() => ({ getTrigger: ..., getOpen: ..., align?, autoPlace? })}` and keep the `fixed left-0 top-0 z-50 will-change-transform` positioning classes on the panel. The action portals to `document.body`, auto-places above/below, and repositions on resize/scroll; components keep their own open/close, keyboard, and outside-click handling. The `KebabMenu` component (`src/lib/components/KebabMenu.svelte`) follows this pattern for a three-dot action menu: it takes `items` (`{ id, label, onClick, disabled?, icon? }`), keeps its own open state, and closes on item click, Escape, outside pointer-down, and scroll.
- Icons live as single-purpose components in `src/lib/icons/` (e.g. `PlusIcon.svelte`, `RefreshIcon.svelte`, `ChevronDownSmallIcon.svelte`), one component per glyph, each taking an optional `className` prop and rendering an `aria-hidden` SVG with `currentColor` fill/stroke. Every icon used in the project — including single-use ones — is a component in that directory. When a change involves an icon, reuse an existing component from `src/lib/icons/` if the glyph already exists, otherwise add a new component there; never inline an SVG in a component. `Button` renders icon snippets inside its `icon()` snippet and sizes them via `[&_svg]:h-full`, so icon components need no default size class; direct (non-Button) usage passes a sizing `className`. The `Spinner` component stays in `src/lib/components` (it is a loading indicator, not an icon glyph).
- Buttons that would move focus away from the editor (preview toggles, mobile drawer button, list-collapse button) pass the `Button` `preventFocusSteal` prop, which calls `preventDefault` on `pointerdown` so the button never takes focus while `click` still fires; raw non-`Button` controls that must not steal focus (e.g. listbox option buttons) use `onpointerdown={e => e.preventDefault()}` for the same effect.
- The CSV grid model (`src/lib/components/use-grid-model.svelte.ts`) tracks per-cell `committed` flags so pure navigation never serializes trailing empty cells into the CSV; preserve the self-echo reconciliation (an incoming `value` differing only by trailing all-empty rows is treated as a self-echo, not a rebuild). The full model mechanics are documented in `docs/spec.md`.
- The `DataGrid` component (`src/lib/components/DataGrid.svelte`) renders the CSV and Properties grids. Sorting uses the shared two-arrow header pattern from the `ui-patterns` reference and goes through `model.sortRows(columnIndex, direction)` (explicit direction, no toggle); the grid's outer edges come from the table's `border-t`/`border-l` only, so column-width math must subtract `TABLE_LEFT_BORDER` (1px). Cell editors are `<textarea>`s (an `<input>` cannot hold `\n`): `Shift+Enter` inserts a newline, `Enter` commits and moves down, and a multiline value renders `rows=1` until its cell is focused, when the editor floats as an absolute overlay (5-line cap, then `overflow-y:auto`) keeping the cell's selection-outline border; header editors keep `rows=2` growth because the fixed header band would clip an overlay. The grid renders as two sibling tables (header + body) inside a flex column where only the body wrapper scrolls; the header wrapper mirrors the body's `scrollLeft` and forwards wheel deltas, and sticky row-number/header cells are per-table. Resizable columns use the shared fixed-layout + `<colgroup>` model driven by the shared `createColumnResize` composable (`src/lib/components/use-column-resize.svelte.ts`): it owns the drag state and width math (capture rendered `offsetWidth`s on first resize, mid-column splitters re-partition two adjacent columns, the trailing splitter expands the table beyond the container, auto-scrolls the body wrapper fully right so the splitter stays visible while dragging, and absorbs a left drag in the previous column so the table's minimum width is the container width) while the component supplies the lookups (column count, scroll container, header-cell measure, per-column minimum, fixed reserved width, storage key). Widths scale all columns proportionally on container resize, targeting `max(minimum × columnCount, container − rownum − border)` so an overflowing table keeps its horizontal scroll. The resize observer must watch the outer viewport, never the body wrapper, so the wrapper's own scrollbar appearing never triggers a re-fit that collapses an intentionally overflowing table. A `storageKey` prop persists resized widths to `localStorage` (via `$lib/column-width-storage.ts`, keyed per grid) and restores them on mount. Component props and cell-editing behavior are documented in `docs/spec.md`.
- Effects that reconcile an external input into editable `$state` (e.g. `CsvPreview` re-parsing `content` into grid rows) follow the `$effect` state-write guard from the shared `svelte` reference: track the last consumed input so each change is parsed at most once, since non-round-trippable text (like content shown after a type switch) would otherwise loop forever.
- The admin `DataTable` (`src/lib/components/DataTable.svelte`) sorts via the shared two-arrow header pattern from the `ui-patterns` reference; `handleSortClick(column, direction)` passes the explicit direction through `onSort`. Derived column widths/min-widths are applied as inline `style` on the cells, never as utility classes built at runtime (see the shared `tailwind` reference). Resizable columns (opt-in via the `resizable` prop) reuse the shared `createColumnResize` composable, keeping the checkbox column fixed and honoring each column's numeric `minWidth` as its floor. When a `storageKey` prop is set, resized widths persist to `localStorage` via `$lib/column-width-storage.ts` and are restored on mount. Component behavior is documented in `docs/spec.md`.
- The browser layout (`src/routes/(browser)/+layout.svelte`) is responsive: the first page of summaries is preloaded server-side and seeded into `useDocuments` (falling back to a client `refreshList()` when no seed was provided), and below the `md` breakpoint the panes collapse into full-screen pages, with the document list reachable via a `MobileDrawer` that reuses the shared `documentList` snippet. Pane visibility on mobile is expressed with literal CSS breakpoint classes (`hidden md:flex` on the editor pane and list wrapper, `md:w-[var(--aside-w,100%)]` on the list) so the SSR first paint is correct without JS; `isMobile` only drives the drawer, splitter, and editor toolbar layouts. Its Escape handling follows the shared dialog keydown protocol so it never double-fires with `BaseDialog`. Layout and responsive behavior are documented in `docs/spec.md` and `docs/design.md`.
- The admin console (`src/routes/admin/`) keeps its Properties/Documents tabs as real SvelteKit routes with a `+layout.server.ts` guard, and holds `useAdminSettings`/`useAdminDocuments` and the `useAdminAuth` state machine in `+layout.svelte` (a thin orchestration layer) so the settings draft and documents data survive tab switches. The shared `Tabs` component serves both the route-driven console tabs (links keyed by `pathname`) and a state-driven mode for dialogs (button tabs with `aria-pressed`; omit `pathname`). The admin edit-document dialog uses the state mode to split **Details** (header fields plus a document-type dropdown) from **Content** (lazily loaded `CodeEditor`), and doubles as the add-document dialog (`mode` prop): add mode hides the key/attribution fields and creates via the `/api/admin/documents` POST dispatch, while edit content edits go through the same `updateDocument` content path as normal saves so version snapshots are recorded. Routing, auth flow, and login-page behavior are documented in `docs/spec.md` and `docs/design.md`.
- Document access control is enforced server-side through `resolveDocumentAccess` (`src/lib/server/documents.ts`), which returns `canView`/`canEdit`/`canDelete`/`canManageAccess` for a `Viewer` (`src/lib/server/viewer.ts`). Anonymous viewers are identified by IP and own a document only when `owner_user_id is null` and `created_by` matches their IP; registered users own via `owner_user_id`, can edit any public or shared document, and delete/manage only documents they own. Documents default to `is_public = true`; only a logged-in owner (or admin) may change visibility or the share list. An admin session resolves to an `admin` viewer that bypasses access entirely (all flags true, no visibility filter), so the admin sees every document in the list and can open private ones in the browser app. Route handlers resolve the viewer once and pass the resulting flags through; the client `owned`/`editable` flags come from the listing/load data, never a client-side guess.
- User accounts live in the `users` table (unique lowercase `username` and `email`, `status` default `'active'`); sharing and per-user config use the `document_shares` and `user_config` tables. User auth (`src/lib/server/user-auth.ts`) uses a signed `sub`-carrying session token separate from the admin token, and `src/lib/server/password.ts`/`rate-limit.ts` hold the shared password hashing and login rate-limit primitives (re-exported by `admin-auth.ts`); login rate limits persist in the `login_attempts` table so they survive restarts and are shared across instances. `/api/auth/*` handles register/login/logout/session; registration and login claim same-IP anonymous documents via `claimAnonymousDocuments`. Inactive (`status = 'inactive'`) users are rejected at login, excluded from user search, share resolution, and server-side viewer resolution, and the session endpoint reports `user: null` so existing sessions are dropped. The admin Users tab manages users through `/api/admin/users` (list/search/sort, create, update username/email/password/status, delete; deleting a user leaves documents ownerless/anonymous and removes share rows via cascade).
- Booleans are bound as parameters only through the `Db` interface; the SQLite adapter converts boolean params to `0`/`1` (`src/lib/server/db-sqlite.ts`) so `is_public = $1` stays portable, while literal `true` in SQL works on both backends. The admin documents table exposes an editable `is_public` column; admin routes bypass viewer access control.
- Admin document/user imports and exports use the same record shapes so an export round-trips through import: documents as `{ key, name, content, documentType, tags, isPublic }`, users as `{ username, email, status, passwordHash }` (the scrypt hash is exported so credentials survive a re-import; plaintext passwords never leave the server). `exportDocumentsForAdmin`/`exportUsersForAdmin` (`src/lib/server/documents.ts`/`users.ts`) drive the `/api/admin/*/export` GET routes; the toolbar **Export** button passes the selected ids when any are chosen and otherwise exports all records. Document import accepts an optional `key` (validated for batch uniqueness, and when it already exists the record merges/upserts into that document instead of erroring, auto-generating otherwise); user import enforces batch uniqueness for both `username` and `email` and accepts `password` or `passwordHash` (never both).
- `sql/schema.sql` is the source of truth for the dev schema. `createSqliteDb` in `src/lib/server/db-sqlite.ts` applies it idempotently (`create table if not exists`) on open, so the dev DB file persists across restarts and dev data survives. New tables appear automatically on the next open, but column changes to existing tables are not applied (SQLite lacks `add column if not exists`); apply those as incremental DDL from the temporary scratch script `.tmp/sqlite-dev.sql` before restarting the dev server. To fully reset the dev DB, delete `.data/share-text-dev.sqlite` and restart. Prod migrations live in `src/lib/server/db.ts` and are additive only (`create table if not exists` / `alter table ... add column if not exists`) so a running app never drops or rebuilds the database.
- Temporary scratch files created during work (plans, proposals, scratch notes) go in the `.tmp/` folder, never in source directories.

## Keeping references in sync

- When a code change establishes or revises a project-specific convention, update this `AGENTS.md` in the same change.
- When a code change establishes or revises a generic reusable convention, update the appropriate file under `$AI_CONFIG_DIR/references/` in the same change rather than duplicating it here.
- Shared reference files under `$AI_CONFIG_DIR/references/` must remain generic and implementation-agnostic. Do not include project-specific file paths, component names, routes, or other internal identifiers in those references — put project-level details in this `AGENTS.md` instead. See `ai/references/README.md` for the brief style guide.
- This `AGENTS.md` holds project-specific *development conventions* — rules an agent must follow when writing code — not feature descriptions, implementation narratives, or user-facing behavior. Keep each bullet to the rule plus the briefest rationale. Implementation/architecture detail belongs in `docs/spec.md` and user-facing behavior in `docs/design.md`; generic reusable rules belong in `$AI_CONFIG_DIR/references/`.
