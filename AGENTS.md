# Share Text Agent Conventions
## Agent progress

- Follow `~/.agents/references/agent-progress.md` for bounded, observable progress and repeated-approach control.

## Skill routing

- Use the `skill-routing` skill for non-trivial, composite, or ambiguous requests to select and sequence the appropriate skills.
- Honor the selected skills' approval, verification, and scope constraints.

## File editing

When modifying files, make edits using the smallest possible range.

* Select a range containing **only the lines that actually change**.
* The edit body must contain the **complete final content of that selected range**.
* Do not include unchanged lines before or after the changed range as implicit context.
* Do not use lines below the selected range to indicate where the edit ends.
* After another edit changes the file, re-read the relevant section before issuing another line-based edit; never rely on stale line numbers.
* If an edit is rejected because the range/body is inconsistent, re-read the current file and issue a new minimal edit rather than retrying the same edit.
* Prefer a uniquely identifiable small text range over a large line-number range when the editing interface supports it.

## Development Guide

Read this `AGENTS.md` and the applicable shared reference files under `$AI_CONFIG_DIR/references/*.md` before writing or reviewing code. When reviewing code, follow the `review` skill definition, reporting findings with severity, location, rule, and fix. When instructions are ambiguous about what to change or how to approach a task, ask the user to clarify or present up to three concrete options before making changes, to avoid unwanted edits. This includes how an element is displayed: if the rendering convention for a value is not established (e.g. the document type shown to visitors), ask before guessing a visual style.

## Project conventions

- The canonical source for the shared UI primitives, icons, actions, and generic scripts is the sibling `ui-lib` project. Vendor them through the `unify` skill and port a shared-component fix back there in the same change; `ui-lib`'s parity gate fails otherwise.
- Code changes are applied in a separate git branch and worktree under `.worktrees/` per the shared `~/.agents/references/git.md` worktree practice, unless the user opts to apply them on top of the current worktree. Create worktrees with `node scripts/create-worktree.mjs <branch>` from the default worktree; it copies the gitignored local dev files (`.env.local` and all files under `.data/`) and sets `DEV_TAG=<branch>` in the new worktree's `.env.local` so the bottom-left worktree-tag block identifies the branch.
- Server persistence goes through the `Db` interface (`src/lib/server/db-types.ts`), writing engine-agnostic SQL with `$n` placeholders and `current_timestamp` so DDL stays portable across adapters. Follow the SQL conventions in `~/.agents/references/sql.md` (including binding a placeholder once per occurrence). Multi-statement writes that must be atomic go through `db.transaction(fn)`, running every statement against the injected query (never `getDb().query`) so the sequence stays on one connection; the SQLite adapter serializes all statements so a transaction cannot be interleaved.
- Mutations are logged via `$lib/server/logging` with key identifying info (document id, name, size, IP, `elapsed_ms`).
- Document tags are stored as a JSON array of `{ name, color }` objects in the `documents.tags` column; `color` must be one of the hex `TAG_COLORS` in `src/lib/tag-colors.ts`, and chips/dropdowns render via the `tagChipStyle`/`tagDotStyle` inline-style helpers there (class helpers `tagChipClass`/`tagDotClass` carry the non-colour base styles). Tag badges render with the `Chip` component (`src/lib/components/Chip.svelte`). The tag editor is the shared `TagInput` (string model): `TagsDialog` maps its `{ name, color }` array to `string[]` at the boundary and passes `chip`/`option` snippets for colored rendering.
- Document types follow the shared `type-registry` reference: the closed value set lives in `src/lib/document-type-values.ts`, the type definitions (language extensions, validators, formatters, converters, preview, toolbar actions) in `src/lib/document-types.ts`, and pure parse/format utilities in `src/lib/document-type-utils.ts`. Each type entry lazy-loads heavy dependencies (language modes, parsers) via dynamic `import()` inside the definition so they are not in the initial bundle. Consumers dispatch through `getDocumentType(value)` and never branch on specific type values.
- Editor preview modes are driven by the `preview`/`editor` URL query params via `usePreviewMode` (`src/lib/components/use-preview-mode.svelte.ts`). The toolbar always shows two toggle buttons (Editor view / Preview view), never a cycle button, each carrying `aria-pressed` and `disabled` when it is the sole active pane; the toggles/preview params are ignored for layout when the type has no preview. Split layout and `Splitter` orientation are documented in `docs/spec.md`.
- Editable form dialogs that persist data on Apply/OK (settings, tags, sharing, admin edit user/document) use the OK/Apply + Reset pattern and the discard-unsaved-changes confirm-on-dismiss behavior from the shared `ui-patterns` reference: the discard `ConfirmDialog` passes `confirmOnDismiss` so its own dismiss affordances perform the discard. Action dialogs that mutate data only on confirm (e.g. the document format dialog) skip both the discard confirm and the disabled-when-clean primary: dismissing loses only a parameter, and confirming the unchanged parameter is still the intended action.
- Form inputs place the caret at the end of the value when focused by keyboard (Tab/Shift+Tab) rather than letting the browser select the whole value: attach the shared `useCaretAtEndOnKeyboardFocus` action (`src/lib/components/use-caret-at-end-on-keyboard-focus.svelte.ts`) to the form's container, never per-input (mouse-initiated focus keeps its natural caret via the action's mousedown suppression).
- Dialogs built on `BaseDialog` are dismissed by its close affordances (top-right close icon, overlay click, Escape), all wired to the same `onCancel`; never add a footer Cancel/Close button that duplicates that `onCancel` — a footer action must do something distinct (persist via OK/Apply, reset, or confirm). `ConfirmDialog` therefore renders only its confirm action button. `BaseDialog` takes an optional `closeLabel` (default: the i18n close-dialog label, resolved via `$derived` so locale switches re-resolve); `ConfirmDialog` takes `confirmColor` and an optional `pending` passed through to its confirm `Button`. User-facing strings in shared components stay overridable via optional props defaulting to `getI18nContext()` labels — never import another project's i18n.
- Content versions are keyed by the immutable numeric `documents.id` (never the app-facing key) so an admin key change never migrates version rows; only the newest `MAX_DOCUMENT_VERSIONS` (default 20) snapshots are kept per document. The version data model and `HistoryDialog` behavior are documented in `docs/spec.md`.
- Overlay option panels (dropdowns, tag suggestions) position via the shared `positionPanel` action (`src/lib/position-panel.svelte.ts`): attach it to the panel with `use:positionPanel={() => ({ getTrigger, getOpen, align?, autoPlace? })}` and keep the `fixed left-0 top-0 z-40 will-change-transform` classes on the panel (`z-40`: overlays stay below the `z-50` dev worktree-tag block). Trigger-and-item overlay menus (the three-dot `KebabMenu` and the globe `LanguageMenu`) share the `Menu` primitive (`src/lib/components/Menu.svelte`), which owns the trigger button, `positionPanel` panel, open/close/toggle, roving real-focus navigation (open on ArrowDown, ArrowUp/ArrowDown/Home/End with disabled-skip, hover syncing `activeIndex` and focus), and Escape/outside-pointer/scroll dismissal with focus returned to the trigger; new menus should be thin `Menu` instantiations, never a re-implementation. Menus needing phone presentation pass `phoneSheetTitle` + `closeLabel` for the bottom-sheet branch (titled sheet with drag-to-close via `dragCloseDown`, safe-area padding, `min-h-11` rows, scroll-close disabled); in-dialog dropdowns keep the anchored popover on all viewports. `SelectDropdown` is the combobox family (its own component, `aria-activedescendant` highlight, no roving focus) — do not fold it into `Menu`. The positioning/behavior mechanics are documented in `docs/spec.md`.
- Z ladder: sticky/grid headers `z-10`/`z-20`, overlays (dialog scrim, drawer, menus, dropdown panels, tooltip) `z-40`, dev tag `z-50` — keep overlays at or below `z-40` so the tag is never covered.
- Shared dropdown lifecycle (`useDropdown`: outside-click/Escape/scroll-close) and list-highlight state (`useListSelection` + `revealInScrollport`) live in `src/lib/actions/`; dropdown surfaces reuse them instead of re-implementing open/close and highlight tracking.
- Icons live as single-purpose components in `src/lib/icons/` (e.g. `PlusIcon.svelte`, `RefreshIcon.svelte`, `ChevronDownSmallIcon.svelte`), one component per glyph, each taking an optional `className` prop and rendering an `aria-hidden` SVG with `currentColor` fill/stroke. Every icon used in the project — including single-use ones — is a component in that directory. When a change involves an icon, reuse an existing component from `src/lib/icons/` if the glyph already exists, otherwise add a new component there; never inline an SVG in a component. `Button` renders icon snippets inside its `icon()` snippet and sizes them via `[&_svg]:h-full`, so icon components need no default size class; direct (non-Button) usage passes a sizing `className`. The `Spinner` component stays in `src/lib/components` (it is a loading indicator, not an icon glyph).
- Buttons that would move focus away from the editor (preview toggles, mobile drawer button, list-collapse button) pass the `Button` `preventFocusSteal` prop, which calls `preventDefault` on `pointerdown` so the button never takes focus while `click` still fires; raw non-`Button` controls that must not steal focus (e.g. listbox option buttons) use `onpointerdown={e => e.preventDefault()}` for the same effect.
- Every focusable element carries `outline-none` and a `focus:` state mirroring its `hover:` styles (e.g. `focus:border-cyan-500`, `focus:text-cyan-300`), so keyboard focus never shows the native outline and reuses the established hover indicator; elements with no hover style get an explicit cyan-ring or color-shift focus indicator instead (see the shared `accessibility` reference). Icon-only containers are sized by padding + glyph (`p-*`), never fixed `h-* w-*`; when a compact visual box is needed, extend the tap/keyboard hit area with `before:-inset-*` rather than enlarging the box (see the shared `responsive-design` reference).
- The CSV grid model (`src/lib/components/use-grid-model.svelte.ts`) tracks per-cell `committed` flags so pure navigation never serializes trailing empty cells into the CSV; preserve the self-echo reconciliation (an incoming `value` differing only by trailing all-empty rows is treated as a self-echo, not a rebuild). The full model mechanics are documented in `docs/spec.md`.
- The `DataGrid` component (`src/lib/components/DataGrid.svelte`) renders the CSV and Properties grids. Sorting uses the shared two-arrow header pattern via `model.sortRows(columnIndex, direction)` (explicit direction, no toggle); column-width math must subtract `TABLE_LEFT_BORDER` (1px) because the table's outer edges come only from `border-t`/`border-l`. Cell editors are `<textarea>`s (an `<input>` cannot hold `\n`): `Shift+Enter` inserts a newline, `Enter` commits and moves down. Resizable columns use the shared fixed-layout + `<colgroup>` model via `createColumnResize` (`src/lib/components/use-column-resize.svelte.ts`), with widths persisted via `$lib/column-width-storage.ts` when a `storageKey` is set, and the resize observer must watch the outer viewport, never the body wrapper. Even before manual resizing, the split header/body tables must share one computed width array so their columns stay aligned. Passing `editable={false}` puts the grid in read-only mode: keep scrolling/selection/copy, but disable mutating toolbar actions, sorting, resizing, and cell edits. All mechanics are documented in `docs/spec.md`.
- Effects that reconcile an external input into editable `$state` (e.g. `CsvPreview` re-parsing `content` into grid rows) follow the `$effect` state-write guard from the shared `svelte` reference: track the last consumed input so each change is parsed at most once, since non-round-trippable text (like content shown after a type switch) would otherwise loop forever.
- The admin `DataTable` (`src/lib/components/DataTable.svelte`) sorts via the shared two-arrow header pattern, passing the explicit direction through `handleSortClick(column, direction)`. Derived column widths/min-widths are applied as inline `style` on cells, never runtime-built utility classes (see the shared `tailwind` reference). Resizable columns (opt-in via the `resizable` prop) reuse the shared `createColumnResize` composable, keeping the checkbox column fixed and honoring each column's numeric `minWidth`; a `storageKey` persists widths via `$lib/column-width-storage.ts`. Behavior is documented in `docs/spec.md`.
- The browser layout (`src/routes/(browser)/+layout.svelte`) is responsive: the first page of summaries is preloaded server-side and seeded into `useDocuments` (falling back to a client `refreshList()` when no seed was provided), and below the `lg` breakpoint the panes collapse into full-screen pages, with the document list reachable via a `MobileDrawer` that reuses the shared `documentList` snippet. Pane visibility below `lg` is expressed with literal CSS breakpoint classes (`hidden lg:flex` on the editor pane and list wrapper, `lg:w-[var(--aside-w,100%)]` on the list) so the SSR first paint is correct without JS; `isMobile` only drives the drawer, splitter, and editor toolbar layouts. Its Escape handling follows the shared dialog keydown protocol so it never double-fires with `BaseDialog`. Layout and responsive behavior are documented in `docs/spec.md` and `docs/design.md`.
The admin console keeps its tabs route-driven under `src/routes/admin/`, preserves shared state across tab switches in `+layout.svelte`, and uses the shared `Tabs` component for both route-driven and state-driven sub-tabs. Keep the admin edit-document dialog as a responsive Details/Content two-pane layout, keep Documents and Users deletion-toolbar-driven with no per-row delete buttons, and keep the admin tabs limited to General/Properties/Documents/Users. Properties-editor changes must replace the known-settings draft subset rather than merging deleted keys back in.
- Document access control is enforced server-side through `resolveDocumentAccess` (`src/lib/server/documents.ts`), which returns `canView`/`canEdit`/`canDelete`/`canManageAccess` for a `Viewer` (`src/lib/server/viewer.ts`). Anonymous viewers own a document only when `owner_user_id is null` and `created_by` matches their IP but can never manage access (`canManageAccess` is always `false` for them), so the Share dialog/button and the access API are login-gated; registered users own via `owner_user_id`, can edit any public or shared document, and delete/manage only what they own; an admin viewer bypasses access entirely (no visibility filter). Documents default to `is_public = true`; only a logged-in owner (or admin) may change visibility or the share list. Route handlers resolve the viewer once and pass the resulting flags through — the client `owned`/`editable` flags come from the listing/load data, never a client-side guess. Sharing resolves sharees by username or email; an admin may share with any registered user including inactive (`setDocumentAccess`'s `includeInactive`), and the access `PUT` — as well as the `sharedWith` field of the admin edit-document `PUT` — is all-or-nothing: it rejects the whole update with 400 (listing the unresolvable sharees) rather than partially applying or silently dropping them. The user directory search (`/api/users/search`) is admin-only; the Share dialog seeds normal-user suggestions from previously-shared active users (`/api/users/recent-sharees`) and never enumerates the directory.
- Sharee inputs — the Share dialog and the admin edit-document dialog's **Shared with** field — use the shared `ShareeCombobox` component (`src/lib/components/ShareeCombobox.svelte`), which owns the debounced suggestion search, add/remove chip editing, and colored chip rendering; consumers pass a `search(query) => Promise<User[]>` provider (directory search for admin contexts, previously-shared users for the Share dialog) rather than re-implementing the combobox.
- User accounts live in the `users` table (unique lowercase `username` and `email`, `status` default `'active'`); sharing and per-user config use the `document_shares` and `user_config` tables. User auth (`src/lib/server/user-auth.ts`) uses a signed `sub`-carrying session token separate from the admin token; `src/lib/server/password.ts`/`rate-limit.ts` hold the shared password-hashing and login rate-limit primitives (re-exported by `admin-auth.ts`), with limits persisted in the `login_attempts` table. Inactive users are rejected at login and excluded from user search, share resolution, and viewer resolution. The admin Users tab manages users through `/api/admin/users` (create, update username/email/password/status, delete; deleting a user leaves documents ownerless and removes share rows via cascade).
Per-account preferences persist through the login-gated `GET`/`PUT /api/user/preferences` API and `src/lib/server/user-config.ts`; keep the whole preference set atomic and sign the session out on 401s from the preferences or owned-documents APIs. The user settings area remains route-driven under `/settings` with Profile/General/Documents tabs, a shared Apply/Reload/Reset footer across General, and a toolbar-driven Documents tab. The account button in the document list and collapsed rail stays a single Settings gear (admin → `/admin`, user → `/settings`).
- Booleans are bound as parameters only through the `Db` interface; the SQLite adapter converts boolean params to `0`/`1` (`src/lib/server/db-sqlite.ts`) so `is_public = $1` stays portable, while literal `true` in SQL works on both backends. The admin documents table exposes an editable `is_public` column; admin routes bypass viewer access control.
- Admin document/user imports and exports use the same record shapes so an export round-trips through import: documents as `{ key, name, content, documentType, tags, isPublic }`, users as `{ username, email, status, passwordHash }` (the scrypt hash is exported so credentials survive a re-import; plaintext passwords never leave the server). The toolbar **Export** button passes the selected ids when any are chosen, otherwise exports all records. Document import accepts an optional `key` (validated for batch uniqueness, upserting into the existing document when it already exists); user import enforces batch uniqueness for `username` and `email` and accepts `password` or `passwordHash` (never both).
- `sql/schema.sql` is the source of truth for the dev schema. `createSqliteDb` in `src/lib/server/db-sqlite.ts` applies it idempotently (`create table if not exists`) on open, so the dev DB file persists across restarts and dev data survives. New tables appear automatically on the next open, but column changes to existing tables are not applied (SQLite lacks `add column if not exists`); apply those as incremental DDL from the temporary scratch script `.tmp/sqlite-dev.sql` before restarting the dev server. To fully reset the dev DB, delete `.data/dev.sqlite` and restart. Prod migrations live in `src/lib/server/db.ts` and are additive only (`create table if not exists` / `alter table ... add column if not exists`) so a running app never drops or rebuilds the database.
- UI text in both the browser app and the admin console goes through the rune-backed i18n store from `$lib/i18n.svelte` (locales `en`, `zh-CN`, `zh-TW`, persisted in `localStorage` under `share-text:locale`). The root `+layout.svelte` creates one store per load via `setI18nContext(createShareTextI18n())` — SSR-safe (a fresh English-defaulted instance per request; creation eagerly applies the saved browser locale and syncs `documentElement.lang`) — and components/composables read it via `getI18nContext()` (a shared English default is returned only when no provider exists, i.e. isolated component tests). Follow the shared `svelte-i18n` reference: the source dictionary is `as const` and the other locales are typed `Record<MessageKey, string>` so a missing translation fails the build; and `i18n.t()` is called in templates/`$derived`, never in a `$props()` default — shared-component default labels resolve via `$derived(prop ?? i18n.t('key'))`. Plain `.ts` API helpers (`admin.ts`, `owned-documents.ts`) cannot call `getContext` and receive the store explicitly as `i18n`. English-count pluralization (e.g. "{n} document(s)") is handled with singular/plural key pairs chosen by the caller; setting labels/descriptions are translated client-side via the `settingLabel`/`settingDescription` helpers (`setting.<key>` message pairs, `settingLabel(i18n, key) ?? setting.label` fallback in `AdminPropertiesView` and the `useAdminSettings` toasts/validation), while messages produced by the server (API `error` fields) stay English. The language selector is the `LanguageMenu` component (`src/lib/components/LanguageMenu.svelte`, globe icon, `positionPanel` menu) rendered in the full-width app header; document type labels and format titles stay untranslated.
- App headers are a full-width top row shared by the browser, admin, and settings layouts: title left, `ThemeMenu` + `LanguageMenu` + identity actions (settings/login, sign-out, back navigation) right, all on the same `px-3 py-3 sm:px-4` metrics. The document-list pane owns only its list toolbar (new, refresh, search, plus the collapse button as the mobile-drawer close affordance); the desktop list-collapse toggle lives in the browser header and passes `preventFocusSteal`. Collapsing hides the pane entirely (no collapsed rail, matching tts) with a width slide. Icon-only `Button` sizes follow tts (`sm`: `p-2`/`before:-inset-2`, `md`: `p-3`).
- The browser header Login button opens an embedded `UserAuthPanel` dialog (bindable `mode` drives the dialog title) instead of navigating to `/login`; on success the layout re-checks the session and refreshes the list so the header identity flips without navigation. A normal-user sign-in stays on the browser page; an admin sign-in redirects to `/admin/general` (the guard's `beforeNavigate` hook prompts first on dirty editors, matching the `/login` page behavior). `/login` serves no form: unauthenticated visitors are redirected to `/?login=1`, which auto-opens the dialog once (param stripped via `replaceState`, no navigation). Explicit sign-out (admin console, settings) lands on `/`; only expired sessions redirect to `/login`.
- Selector menus (`LanguageMenu`, `ThemeMenu`) are thin `Menu` instantiations following the tts styling: content-width panel (no fixed `panelClass`), `transition-none` items with the checked option in cyan text only (no background highlight or dot), and the padded trigger with the `before:-inset-*` hit-area extension.
- Temporary scratch files created during work (plans, proposals, scratch notes) go in the `.tmp/` folder, never in source directories.

## Keeping references in sync

- When a code change establishes or revises a project-specific convention, update this `AGENTS.md` in the same change.
- When a code change establishes or revises a generic reusable convention, update the appropriate file under `$AI_CONFIG_DIR/references/` in the same change rather than duplicating it here.
- Shared reference files under `$AI_CONFIG_DIR/references/` must remain generic and implementation-agnostic. Do not include project-specific file paths, component names, routes, or other internal identifiers in those references — put project-level details in this `AGENTS.md` instead. See `~/.agents/references/conventions-extraction.md` for the brief style guide.
- This `AGENTS.md` holds project-specific *development conventions* — rules an agent must follow when writing code — not feature descriptions, implementation narratives, or user-facing behavior. Keep each bullet to the rule plus the briefest rationale. Implementation/architecture detail belongs in `docs/spec.md` and user-facing behavior in `docs/design.md`; generic reusable rules belong in `$AI_CONFIG_DIR/references/`.
- When the user corrects a mistake, approves a fix, or states a new convention, invoke the `learn` skill so the lesson is not repeated.
